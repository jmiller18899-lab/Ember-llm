# Ember v0.1.0 re-pretraining corpus

Status: **configuration and CPU builder available; full corpus not yet verified.**
See the [builder runbook](ember-v0.1.0-builder.md). `config/corpus_v0.1.0.json` authorizes no
corpus build, tokenizer training, GPU training, promotion, or deployment.
`ember-v0.0.7-hf-ready.zip` remains the authoritative package and
`ember-v0.0.31-t4` step 479 remains the best checkpoint.

## Why a new corpus instead of another fine-tune

- v0.0.31 copies 43/90 held-out literals exactly (first-token top-1 89/90) and
  passes the legacy routing evaluator at 84/90, but scores **0/36** on
  semantic-v1: every tool call has the right envelope, tool name, and argument
  key with the wrong value (`reports/ember-v0.0.31-semantic-verdict.json`).
- The tested fine-tuning trajectories showed a learning/preservation trade-off:
  placement gains came with losses in familiar routing. The separate training-
  balance branch recommends punctuation weight 0.05 from local loss measurements;
  its full 40-step trajectory has not been run. These results do not establish
  that every further fine-tuning recipe must fail.
- The base model has 27,662,848 parameters (`n_layer=6`, `n_embd=512`, tied
  16,384-piece embedding) and was pretrained on 15,005,553 tokens: 0.54 tokens
  per parameter, validation loss 4.33. Learning copying and tool routing together
  on more data is a hypothesis worth testing, not a demonstrated explanation of
  the prior failures or a guarantee that pretraining will fix them.

v0.1.0 therefore changes the base, not the recipe: same architecture, a real
token budget, and the envelope-copy curriculum present from step 0.

## Budget

| | v0.0.7 | v0.1.0 draft |
| --- | ---: | ---: |
| Target tokens | 15,000,000 | 300,000,000 |
| Hard gate | 10M–20M | 250M–350M |
| Tokens per parameter per epoch | 0.54 | 10.8 |
| Recommended epochs | 1 | 2 (~21.7 tokens/parameter) |
| Validation ratio | 2% | 0.5% (~1.5M tokens) |
| Tokenizer | 16,384 SentencePiece BPE | unchanged size; retrained on the new seed sample |

Throughput note: the 27.66M model in fp16 on a T4 processes roughly 30–40k
tokens/s, so one epoch is on the order of 2–3 GPU hours. Two epochs fit in a
single working day of `t4-small` time.

Changes from v0.0.7 and why:

- **OASST1 cannot scale.** It yielded about 3M usable English tokens for
  v0.0.7 under the headroom-shortfall rule. It stays as a 1% human-written
  slice, and SmolTalk supplies the rest of the instruction share. SmolTalk is
  model-generated; that is acceptable for a pretraining mix whose purpose is
  format and instruction-following coverage, and it is documented as such.
- **Glaive is finite.** 112,960 rows, roughly 68M tokens. The two Glaive
  categories together take about 40% of it, so both must use the finite-source
  rule (hard minimum 1.0x, preferred 1.3x) that v0.0.7 applied only to OASST1.
- **Agent trajectories drop from 10% to 7%.** OpenHands trajectories are long
  and repetitive; the envelope_copy slice now carries the short, dense
  tool-call signal that the 10% share was partly standing in for.

## The envelope_copy slice

Generated by `jobs/ember_corpus_envelope_copy_v010.py` from the config's
`sources.envelope_copy` block. Stdlib only, deterministic, no network.

Seven document shapes, weighted in the config:

| Shape | Weight | What it teaches |
| --- | ---: | --- |
| tool_call | 0.30 | copy one value from the user turn into the argument slot |
| tool_call_choice | 0.12 | pick the designated value over a same-kind distractor |
| tool_call_multi_arg | 0.10 | copy two values into two slots (`send_message`, `compare_models`) |
| tool_call_with_result | 0.20 | tool call, then a `<|tool_result|>`, then a grounded one-sentence answer |
| two_turn | 0.08 | two requests, two envelopes, EOS only at the end |
| direct_extract | 0.10 | copy at completion position 0, no tool |
| direct_sentence | 0.10 | copy mid-sentence, no tool |

Twelve tools and thirteen value kinds (`short_code`, `long_code`, `digits`,
`model_id`, `url`, `path`, `entity`, `expression`, `mixed`, `city`,
`timezone`, `query`, `service`). Value templates carry over the v0.0.26
format-parity variants so every held-out structure from the 90-case copy
battery is reachable. Three system-prompt styles (`sentence`, `schema`,
`AVAILABLE_TOOLS` JSON) match the frozen semantic-v1 prompts and the
`render_agent_record` convention respectively. Half of single-value prompts
carry two same-kind distractors.

Rendering matches the semantic-v1 prompts: `<|assistant|>\n<|tool|>\n{json}`
with canonical sorted-key JSON, raw JSON in `<|tool_result|>`, one
`<|endoftext|>` per document. About 110 tokens per document at 4.8 chars/token,
so 180,000 candidate documents give roughly 20M candidate tokens for the
15M-token share.

### Held-out hygiene

`Exclusions.from_config` blocks, case-insensitively, every semantic-v1
`argument_variants` value, every `HELD_OUT_VALUES` entry from
`jobs/ember_sft_data_v026.py` (90 held-out copies and their corrupted twins),
the config's explicit `exact_values`, and any value containing a configured
substring (`ZV82`, `9037`, `Detroit`, `Marquette`, `Benton Harbor`, `Tokyo`,
`Chatham`, `Toronto`). 207 exact values are blocked at generation time; the
audit re-checks every emitted target and reports `held_out_leakage`.

### Audit

`audit()` is the envelope-level version of the v0.0.26 format-parity audit:

- every tool appears in every tool-call shape (single-argument tools in
  `tool_call`, `tool_call_choice`, `tool_call_with_result`, `two_turn`;
  two-argument tools in `tool_call_multi_arg`);
- minimum documents per tool, per shape, per kind, and minimum distinct values
  per non-pool kind (pool kinds are `city` and `timezone`);
- each copied value appears in both prompt and completion;
- each `<|tool|>` line follows a bare `<|assistant|>` line, parses, is
  canonical, names a configured tool, and carries exactly that tool's keys;
- every tool called in an `AVAILABLE_TOOLS` document is advertised there;
- exactly one terminal `<|endoftext|>`.

Verified on this draft (`python jobs/ember_corpus_envelope_copy_v010.py
--assert-coverage`): 180,000 documents, `status: PASS`, `held_out_leakage:
false`, 0 failures. `tests/test_ember_corpus_v010.py` pins the config
arithmetic and the slice properties.

## Builder implementation

`jobs/ember_corpus_build_v010.py` implements the six requirements below using
the unchanged v0.0.7 package's corpus utilities and tokenizer wrapper. The old
package's `scripts/build_training_corpus.py` remains the v0.0.7 entry point.
Details and measured evidence belong in the [builder runbook](ember-v0.1.0-builder.md).
The requirements are:

1. A SmolTalk loader (OpenAI-style `messages`, rendered with
   `render_openai_messages`, `apigen-80k` excluded).
2. An `envelope_copy` loader that streams `iter_documents(config)` into
   `CorpusDocument` rows and applies **exact-hash dedup only** for that
   category. MinHash near-dedup on five-word shingles at 0.90 would reject
   templated rows that differ only in the copied value.
3. The finite-source shortfall rule for every source marked `finite_source`.
4. `render_agent_record` must emit `<|assistant|>\n<|tool|>` for tool-call-only
   assistant turns instead of the current `<|assistant|>\n\n<|tool|>`, so the
   Glaive and OpenHands documents agree with the slice and with the frozen
   semantic-v1 prompts.
5. Per-category streaming to disk during selection and split. 300M tokens is
   about 1.9 GB of candidate text before headroom; the in-memory design that
   fit 15M tokens on a 7 GiB runner will not.
6. `corpus_stats.json` gains an `envelope_copy_audit` block copied from the
   generator's audit output.

Build on a CPU job with at least 16 GiB RAM and 20 GB scratch. The build never
launches GPU training.

## Evaluation plan for the resulting checkpoint

The base is new, so v0.0.31's diagnostics are not comparable. The gate that
matters is unchanged: semantic-v1 (`docs/ember-semantic-gate.md`) on full and
INT4 weights, exact tool arguments, grounded tool-result answers, clean stops.
The 90-case copy battery and the familiar 90-case routing battery are reported
for continuity but do not decide promotion.
